# Производительность и передача состояния: как это реально устроено

Разбор предложений по оптимизации (02.08.2026) с вердиктом по каждому пункту
и описанием того, как соответствующая часть уже реализована в коде.
Парный документ: `TECH_DATA_CORRECTNESS.md` (корректность данных — там же
решение «SQLite не сейчас» и его триггеры).

**Главный принцип:** при 228 КБ данных и одной кальянной узкое место — не сервер,
а Wi-Fi заведения и рендер планшета. Оптимизировать без измерений нельзя;
усложнять синхронизацию ради экономии килобайта — вредно.

## Сводка вердиктов

| Предложение | Вердикт | Почему |
|---|---|---|
| Brotli/gzip в nginx | ✅ уже работает | `gzip on` в nginx.conf; app.js летит 18 КБ вместо 55 (проверено curl'ом) |
| HTTP keep-alive | ✅ уже работает | дефолты nginx (клиенты) и Node (`keepAliveTimeout` 5 с > интервала опроса 4 с — соединение переиспользуется) |
| Статика напрямую через nginx | ❌ не делаем | логика кэша (`?v` immutable vs no-cache) живёт в одном месте — `serveFile()`; дублировать её в nginx = два источника истины ради нагрузки, которой нет |
| ETag / Last-Modified | ⏸ отложено | HTML-страницы ~10 КБ гзипом ~3 КБ; выигрыш от 304 незаметен, ревалидация и так есть (`no-cache`) |
| Передавать только изменившийся стол (дельты) | ❌ вредно | см. «Почему полный снимок» ниже |
| Не перерисовывать все 25 плиток | ✅ уже сделано | `gridSignature()` + `updateTimers()`, см. ниже |
| Батчить обновления через rAF | ❌ не нужно | обновления идут раз в секунду и меняют только textContent — жанка нет по построению |
| Не писать диск каждую секунду таймера | ✅ и так не пишем | таймеры — абсолютные метки времени; диск трогается только при действиях |
| Сначала измерить реальные времена | ✅ согласны | единственный пункт «в работу»: замеры в diag.html (см. план) |

## Как реализовано

### 1. Сжатие и кэширование (nginx + serveFile)

- nginx: `gzip on` глобально — JS/CSS/JSON/SVG сжимаются на лету.
  Факт: `app.js` (55 КБ) передаётся как **18 477 байт**.
- `server.js → serveFile()` — вся политика кэша в одном месте:
  - файлы с меткой версии `?v=N` → `Cache-Control: public, max-age=31536000, immutable`
    (браузер больше никогда их не спрашивает; при правке меняется адрес);
  - PNG → `max-age=604800`;
  - всё остальное (HTML, sw.js, nav.js без версии) → `no-cache, must-revalidate`;
  - API → `no-store`.
- Правило деплоя: `?v=N` в index.html и `CACHE = "serp-pult-vN"` в sw.js бампаются
  **последним шагом**, после финальной правки кода.

### 2. Почему полный снимок состояния, а не дельты

Пульт опрашивает `/api/calls` раз в 4 с и получает **всё**: вызовы + полное
состояние столов. Это осознанное решение, а не наивность:

- полный снимок — **самолечащаяся синхронизация**: потерянный пакет, уснувшая
  вкладка, перезаход — всё исправляется следующим опросом без спец-логики;
- дельты требуют версионирования, буферизации пропущенных изменений и merge —
  ровно тот класс багов «планшет и телефон видят разное», от которого проект
  избавился, перенеся состояние на сервер;
- цена вопроса: полное состояние 9 столов — единицы КБ, после gzip — меньше
  килобайта каждые 4 секунды. Экономить тут нечего.

Если когда-то станет тесно (сотни столов) — сначала поднять интервал опроса,
потом думать про WebSocket, и только потом про дельты.

### 3. Рендер пульта: перерисовка только того, что изменилось

`public/pult/app.js`:

- `gridSignature()` — строка-отпечаток структуры зала: какие столы заняты,
  сколько кальянов, номера кругов, вызовы, взведённые тапы. Пересборка DOM
  (`renderGrid`) происходит **только если отпечаток изменился**;
- каждую секунду работает лёгкий путь `updateTimers()`: меняются только
  `textContent` цифр, ширина полосы прогресса и css-классы состояния —
  ни одна плитка не пересоздаётся;
- поэтому нажатия не «съедаются» перерисовкой (старый баг, вылеченный ещё 31.07),
  а нагрузка на рендер iPad минимальна;
- каждая плитка рисуется в try/catch — ошибка одной не роняет сетку.

### 4. Диск: записи только на действиях

`server.js`:

- таймеры хранятся **абсолютными метками** (`startedAt`, `roundStart`) —
  «тикание» не требует ни записи, ни пересчёта на сервере;
- запись на диск — `saveLater()`: отложка 400 мс, схлопывает пачку изменений
  в одну запись; сама запись атомарна (tmp-файл + rename);
- на SIGTERM/SIGINT — `flushAll()`: принудительный сброс всего, рестарт
  не теряет данные (проверено на живых столах при деплоях).

### 5. Сеть клиента: что уже смягчает плохой Wi-Fi

- сервис-воркер «сеть в приоритете, кэш — офлайн-фолбэк»: свежесть без жертв;
- `failStreak >= 3` — один лаг сети не пугает смену баннером «нет связи»;
- экран загрузки объясняет, на каком шаге затык (пульт/связь/столы) и что делать;
- пуш-уведомления не зависят от открытой вкладки — звук играет система.

## Чего не делать без измерений

- не выносить статику в nginx «для скорости»;
- не вводить дельта-синхронизацию состояния;
- не переходить на WebSocket «чтобы было realtime» — опрос раз в 4 с
  покрывает ритм кальянной с запасом;
- не кэшировать API;
- не «оптимизировать» Node — при 1 CPU и 228 КБ данных он простаивает.

Любая из этих идей возвращается в работу только вместе с числом из замера,
которое она должна улучшить.
